# R06c: Testing, what R06 and R06b didn't reach

Bottom line: the belief that "no published practice covers unattended acceptance runs on physical devices" is wrong. Linaro's LAVA and KernelCI both publish a working model: a health check gates every device, a device that fails it is taken offline instead of collecting test failures, infrastructure errors are a separate result from test failures, and the run keeps evidence (logs, screenshots, video in openQA).\[1\]\[2\]\[3\] The repository should adopt that model in its testing skill instead of telling users to invent their own. The test-strategy beliefs are broadly right but need four corrections: Cohn called it the "Test Automation Pyramid", Dodds' trophy has four layers including "Static" and is scoped to JavaScript, Google classifies tests by size *and* scope (not size alone), and Fowler's own bliki says the pyramid's assumption can fail, which matters for command-line programs.

Scope note: this run finished Priority questions E, F and Q1, and part of D. Q11 and Q12 are only partly covered, and tool versions are covered for 15 of the 33 requested tools. The rest is listed in section 9 for a further run.

## TL;DR

- **Hardware acceptance runs have published practice:** LAVA runs a health check on each device, takes a device that fails it offline, separates job health (Complete/Incomplete) from test results, and KernelCI turns "incomplete" infrastructure errors into ERROR or MISS rather than FAIL. Copy this model: a precondition gate, a device-lost abort that records "incomplete" and not "failed", and an evidence bundle.
- **Fault injection is per-platform:** libfiu 1.2 (2023-10-29) and `LD_PRELOAD` on Linux; `DYLD_INSERT_LIBRARIES` on macOS works only on binaries that are not hardened or SIP-protected; Windows Application Verifier "Low Resource Simulation" fails FILE, REGISTRY, HEAP_ALLOC and other API classes with a set probability; Toxiproxy is now 2.13.0 (14 Oct 2026) and adds optional API auth; `tc netem` covers delay, loss, duplication, corruption and reordering on Linux only.
- **Test shape:** for a desktop or command-line program with no network service, Google's definitions make an in-process test "small" and a test that launches the binary "medium". Fowler's bliki says that if high-level tests are "fast, reliable, and cheap to modify - then lower-level tests aren't needed". So a suite heavy on subprocess-level CLI tests against temporary directories is defensible, as long as core logic also has in-process tests.

## 1. Summary

1. LAVA (Linaro) health checks are "run periodically to check for equipment and/or infrastructure failures", and "If a health check fails for any device, that device will be automatically taken offline." This is the published precondition-gate pattern.\[1\]
2. LAVA separates a job *failure* (infrastructure; job health Incomplete) from a failed `lava-test-case`. A failing test case alone does not take a device offline.\[1\]
3. A test can abort itself: "call lava-test-raise <message>. This will return immediately and set the job health to Incomplete." This is the published "device lost, stop, don't record failures" mechanism.\[2\]
4. LAVA's "Looping" health state "continuously submits a health check each time the previous health check completes", for triaging intermittent device or infrastructure faults.\[4\]
5. KernelCI's Maestro maps `incomplete` results with error codes such as Infrastructure, LAVATimeout and Canceled to **ERROR**, and configuration or submit errors to **MISS**, never to FAIL. Incomplete nodes are retried (retry_counter up to 3) before they are reported.\[5\]\[6\]
6. openQA's engine "generates a video, screenshots and a JSON file with detailed results" and records `NEEDLES_GIT_HASH`, the version of the reference images used.\[7\]\[8\] That is a ready-made evidence-bundle checklist.\[3\]\[9\]
7. LAVA 2026.10 is the newest release seen. It is "the last release carrying" the Results→Queries and Results→Charts UI. LAVA 2026.04 dropped Debian 11 and LXC jobs.\[10\]\[11\]
8. libfiu's current version is 1.2, released 2023-10-29. It can inject faults into POSIX calls "without having to modify the application's source code".\[12\]
9. Toxiproxy 2.13.0 (14 Oct 2026) adds optional bearer-token auth (`TOXIPROXY_AUTH_TOKEN`) and warns when the API is unauthenticated on a non-loopback address.\[13\]
10. Windows Application Verifier "Low Resource Simulation" is fault injection. Probabilities are in parts per million (since builds after February 2007), and Microsoft says both the with-faults and without-faults runs are needed.\[14\]\[15\]\[16\]
11. On macOS, dyld ignores `DYLD_*` variables for SIP-protected binaries, and the hardened runtime blocks injection. GitHub's macOS runners have SIP off (secondary), so a shim test can pass in CI and fail on a developer Mac.\[17\]\[18\]\[19\]
12. Fowler's TestPyramid bliki (1 May 2012) credits Cohn's 2009 *Succeeding with Agile*, where it is the "Test Automation Pyramid". It also says the pyramid's premise has exceptions.\[20\]
13. Fowler (2 June 2021) argues the pyramid-versus-honeycomb/trophy dispute is "moot" because the camps define "unit test" differently (solitary versus sociable).\[21\]
14. *Software Engineering at Google* ch. 11 ("Testing Overview", free at abseil.io) defines size (small: single process, no sleep or I/O; medium: single machine and localhost only; large: anywhere) and scope separately. It aims for roughly 80/15/5 by *scope*, and footnotes a fourth size, "enormous".\[22\]
15. No primary source names a tool that reports tests whose result never varies (always pass, never run, always skipped) as a first-class metric. Commercial test-analytics products report skipped counts and "always failing" tests (secondary/vendor).\[23\]\[24\]\[25\]

## 4. Findings

### E. Acceptance and hardware-in-the-loop testing

**What the published practice is.** LAVA is the most complete public reference. Its model, in its own terms:

- **Preconditions that stop a run before it starts.** A *health check* is "a special type of test job, designed to validate that the a test device and the infrastructure around it are suitable for running LAVA tests". If one fails, "that device will be automatically taken offline". Peripherals are part of the check: if a needed USB device "cannot be found in udev", LAVA raises an infrastructure issue and takes the device offline.\[1\] Scheduling enforces the gate: a device in Health "Unknown" gets a health check "as soon as the device has finished any current job but before starting any other submitted job". When no device of a type is Good or Unknown, "test jobs will be held in the Queue".\[4\] Health checks should boot a **golden image** "to provide constant results".\[2\]
- **Device lost mid-run: stop, don't record failures.** LAVA keeps two separate outcomes: *job health* (Complete/Incomplete, meaning infrastructure) and *test-case results* (pass/fail). Going offline "applies to a job failure, not a fail result from a single lava-test-case".\[1\] A test definition that detects lost hardware calls `lava-test-raise <message>`, which "will return immediately and set the job health to Incomplete".\[2\] Each job also has "Global timeouts - to detect and fail a hung job" (Linaro training slides, HKG18).\[37\] KernelCI then maps incomplete results by `error_code`: Infrastructure, LAVATimeout, Canceled and similar become **ERROR**, while configuration and submission errors become **MISS**. It retries incomplete nodes ("retry_counter != 3 are skipped") before reporting.\[5\]\[6\] The published lesson: a disconnected drive or board is an **ERROR/Incomplete with a reason**, never a FAIL against the product.
- **Intermittent device faults.** LAVA's "Looping" mode re-runs the health check continuously "irrespective of how that health check finished" to measure how often a device or infrastructure fault happens. The debugging guide adds: "see if the error can be provoked in a health check and then use looping mode to generate data on how often the error occurs".\[4\]\[38\]
- **Evidence bundles.** openQA's engine "generates a video, screenshots and a JSON file with detailed results", and openQA records test-code and needle versions (`NEEDLES_GIT_HASH`) so a result can be traced to exactly what judged it.\[7\]\[8\] Retention is configurable ("Keep results for", "Keep important results for").\[3\]\[9\] LAVA's debugging guide recommends that tests depending on "a specific **block device** or **filesystem**" add "the output of df or mount" to the log.\[38\] That is cheap environment evidence. Combined into a bundle checklist (our synthesis): run manifest (tool, test-code and reference-data versions), device identity and health state at start, environment dump (`df`, `mount`, `lsusb`, `udevadm` or the OS equivalent), full console log, per-test JSON results, screenshots or video where there is a UI, and the abort reason if Incomplete.
- **Run-size tiers and frequency.** The only primary datum found is LAVA's historical default: device types were created "with a routine health-check frequency of 24 hours".\[32\] No primary source defines smoke, nightly and full tiers for device racks. Google ch. 11 gives the general principle: teams "isolate their large tests ... running them only during the build and release process so as not to impact developer workflow".\[22\] **Recommendation (our inference, labelled):** tier 0 = health check before every run (minutes); tier 1 = smoke per change on one device per type; tier 2 = nightly full suite per device type; tier 3 = full matrix (all devices, all media) before release.
- **Fuego** is a Jenkins-fronted, Docker-packaged host/target framework for embedded Linux, with "over 50 pre-packaged tests", created for LTSI (the LTSI Test Project, launched 2013, "became Fuego on March 2016").\[33\]\[39\] Its current version and maintenance status were **not found**. Treat it as a reference design, not a recommendation.

**Cost, and when it isn't worth it.** No source gave money costs. Each LAVA device type needs "switchable USB hubs, relays, remote power control, multiple serial connections" for full automation (LAVA debugging docs),\[38\] so the fixed cost is the remote power and serial hardware plus a server and worker. Our judgment: it is not worth it when there are fewer than about 2 device types, when releases are rare enough that a scripted manual checklist is cheaper, or when the device behaviour can be faked at the OS boundary (see F). It is worth it once a "device lost" result has been mistaken for a product regression even once.

### F. Fault injection for ordinary applications

| Fault | Linux | macOS | Windows | What proves "handled" |
|---|---|---|---|---|
| Disk full / write error | libfiu `fiu-run` with POSIX failure points (e.g. make `write` fail); a small loopback or tmpfs mount (not verified this run) | `DYLD_INSERT_LIBRARIES` shim, only on unsigned or non-hardened builds | Application Verifier Low Resource Simulation, **FILE** class | Exit code and message as specified; no partial or corrupt output file; original file intact |
| Unwritable folder | `chmod` on a temporary directory (note: root ignores it) | same | ACL deny on a temporary directory | Clear error, non-zero exit, no crash dump |
| Network drop / stall | Toxiproxy 2.13.0 toxics (latency, bandwidth, timeouts); `tc netem` delay, loss, corruption, duplication, reorder, rate | Toxiproxy | Toxiproxy (Windows binaries published) | Timeout fires within the configured bound; retry count as specified; no hang |
| Device removed mid-operation | libfiu failure points on `read`/`ioctl`; real hardware via LAVA-style relays | shim | AppVerifier FILE/handle checks | Run marked aborted with reason; resources released |
| Process killed mid-write | `kill -9` from the test harness at a sync point | same | `taskkill /F` | On restart: data is either old or new, never torn (check fsync/rename pattern) |
| Out of memory | libfiu `malloc` point | shim | AppVerifier HEAP_ALLOC / VIRTUAL_ALLOC | Graceful error, not an abort |

Key sourced points:
- **libfiu 1.2** (2023-10-29) provides a core API to mark failure points and tools that inject failures "in the POSIX API *without* having to modify the application's source code". Ubuntu ships it as `libfiu-dev` 1.2 ("Version: 1.2-2"). It has a Python binding (`python3-fiu`).\[12\]\[40\]
- **Toxiproxy 2.13.0** (14 Oct 2026) adds bearer-token auth, fixes "removing a toxic hanging forever", and fixes "the bandwidth toxic hanging or panicking when rate <= 0". Upgrade from 2.12.0 (18 Mar 2025) if you use bandwidth toxics.\[13\]\[41\]
- **`tc netem`** works at the network-interface level and needs root. It is Linux-only, so it suits CI containers or VMs, not developer laptops.\[31\]\[42\]
- **Windows Application Verifier**: Low Resource Simulation fails API classes (WAIT, HEAP_ALLOC, VIRTUAL_ALLOC, REGISTRY, FILE, EVENT, MAP_VIEW) with a probability. The `/faults` command line on its own "will enable fault injection just for OLE_ALLOC and HEAP_ALLOC", so FILE faults must be configured explicitly. A TIMEOUT skips injection during process startup. Microsoft says to run the suite both with and without faults.\[15\]\[43\]
- **macOS**: `DYLD_INSERT_LIBRARIES` is ignored for SIP-protected binaries and is blocked by the hardened runtime (mandatory for notarised apps; secondary sources). Inject only into unsigned or ad-hoc-signed **test builds**. CI results may differ from developer Macs because GitHub runners have SIP off (secondary).\[17\]\[18\]\[19\]
- **Chaos-engineering tools scaled down:** Google ch. 11 places "Chaos Engineering" at the large end of failure testing.\[22\] For a desktop program, Toxiproxy plus libfiu or AppVerifier is the scaled-down equivalent. No primary source for a desktop-scale chaos tool was found.

**How a test proves the program handled the fault rather than crashed later.** Our synthesis from the sources: (1) assert the *specified* observable outcome (exit code, error text, log line) in the same test; (2) assert invariants after the fault (old file intact, temporary files removed, no lock left); (3) run a follow-up operation in the same process or a restart to show the program is still usable; (4) for AppVerifier, attach a debugger, because its stops are reported there ("If you run an application with those tests enabled and have no crashes, then they are not reporting any problems", AppVerifier FAQ); (5) also run without injection (Microsoft's rule).\[15\]\[16\]

### D. Finding what you don't know is missing

- **Inventories against tests:** no primary-source published practice was found for a feature, command or setting inventory checked against the tests that exercise it. Google ch. 11 gives the principle, not the mechanism: "test everything that you don't want to break" (the "Beyoncé Rule"). It warns that coverage "only measures that a line was invoked, not what happened as a result".\[22\] **Recommendation (our inference):** generate the inventory from the program itself (`--help` output, the settings schema, the command registry). Tag each test with the commands and settings it exercises. Fail CI when an inventory item has no tag. That is a cheap, deterministic check that suits this repository's script style.
- **Mining run history for checks that never vary:** documented practice evidence is the Cilium Tetragon PR, where tests "were always skipped and we never noticed" and "skipped tests can go easily unnoticed". The fix was to parse detailed result files and print a distinct symbol for skipped tests.\[36\] Vendor tools report parts of this: BrowserStack Test Reporting has an "Always failing" smart tag and per-status filters; Codecov Test Analytics lets you "drill into the flaky test count or skipped tests"; Datadog reports "Tests Skipped".\[23\]\[24\]\[25\] **No tool found reports "always passes" or "never executed across N runs" as a named metric.** **Recommendation:** keep JUnit XML from every run (all mainstream runners emit it), and run a script over the last N runs that lists test IDs whose status set is {skipped}, {not present} or {passed}. Treat always-passed tests as mutation-testing candidates (see R06 for mutation tools).

### Q1. Test strategy from primary sources

**Exact definitions.**
- *Fowler, TestPyramid (2012):* "a way of thinking about how different kinds of automated tests should be used to create a balanced portfolio. Its essential point is that you should have many more low-level UnitTests than high level BroadStackTests running through a GUI." UI tests "are: brittle, expensive to write, and time consuming to run." He adds a middle layer of "SubcutaneousTests" through a service layer.\[20\]
- *Fowler, Shapes (2021):* honeycomb and trophy advocates' "unit test" means his *solitary* unit test, and their "integration test" "sounds very much like what I would call a sociable unit test". His larger point, quoting Justin Searls: focus on tests that "establish clear boundaries, run quickly & reliably, and only fail for useful reasons."\[21\]
- *Dodds, trophy:* four layers. Static: "Catch typos and type errors as you write the code". Unit: "Verify that individual, isolated parts work as expected". Integration: "Verify that several units work together in harmony". End to End: "A helper robot that behaves like a user". Scope: JavaScript applications. The integration-heavy advice rests on his claim that "as you move up the pyramid, the confidence quotient of each form of testing increases".\[27\]\[28\]\[29\]
- *Google ch. 11:* size = resources and permissions (small: single process, often single thread, no sleep, I/O or blocking calls; medium: single machine, network only to localhost; large: multiple machines). Scope = how much code is *validated*. Google says it prefers "to keep the real dependencies in place when it is feasible", which matches Fowler's *sociable* style.\[22\]

**Where they disagree.** On ratios only, and Fowler argues the disagreement is mostly about words. On mocks, Google and Dodds both lean sociable, and the pyramid as Fowler describes it allows both styles. The real split is over whether high-level tests are expensive. Fowler's footnote concedes the pyramid holds only when they are, and Dodds argues modern tools have made them cheaper.\[20\]\[29\]

**For a desktop or CLI program with no network service (our recommendation from these sources):**
1. Put core logic behind an in-process API and give it **small** tests (Google), with fakes for the filesystem and clock. These are the fast base.
2. Treat **subprocess-level CLI tests** (launch the binary against a temporary directory and assert on stdout, stderr, exit code and files) as **medium** tests. With no network they are usually fast and deterministic, which is exactly Fowler's footnote case, so they can be a large share, as the trophy suggests.
3. Keep **large** tests (real devices, real installers, other operating systems) in a separate tier run at release (Google), structured per section E.
4. Add static checks (types, linters) as the trophy's base. That fits the repository's checks folder.
5. Judge the suite by Searls' criteria, not by ratios.

## 7. Common mistakes (including AI coding assistants)

1. **Recording a lost device as a product failure.** LAVA and KernelCI separate Incomplete/ERROR from FAIL for this reason.\[5\] Assistants commonly write `assert device_ok()` inside a test, which turns infrastructure loss into a red test. Use an abort path (`lava-test-raise`-style) instead.\[2\]
2. **No precondition gate.** Running a suite on a device that never passed a health check (LAVA runs one before any job when health is Unknown).\[4\]
3. **Assuming `DYLD_INSERT_LIBRARIES` works like `LD_PRELOAD`.** It is ignored for SIP-protected and hardened binaries, and passes on SIP-off CI runners only (secondary).\[17\]\[19\]
4. **Using AppVerifier `/faults` and expecting file faults.** By default it covers only OLE_ALLOC and HEAP_ALLOC. Also, probabilities are parts per million, not percent.\[15\]\[16\]
5. **Testing only with injection on.** Microsoft: both scenarios "must be run".\[15\]
6. **Treating the pyramid or trophy ratio as a rule.** Fowler (quoting Searls) calls ratio debates "a distraction". Google says "every team’s mix will be a little different".\[21\]\[22\]
7. **Calling any test that touches disk a "unit test" and a small test.** Under Google's definitions, disk I/O makes it at least medium.\[22\]
8. **Letting skipped tests disappear.** Tetragon's tests "were always skipped and we never noticed".\[36\] Assistants often add `skip`/`xfail` markers to get CI green. Count skips per run and fail on growth.
9. **Using code coverage as the inventory.** Coverage "only measures that a line was invoked, not what happened as a result" (Google).\[22\]
10. **Leaving an unauthenticated Toxiproxy API on a shared network.** 2.13.0 now warns about this.\[13\]
