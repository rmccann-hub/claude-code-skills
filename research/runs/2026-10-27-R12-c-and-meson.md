# R12: C, built with Meson — research result (27 October 2026)

A professional writing or reviewing C built with Meson today should:
- target C17 for portability, using C23 only where every supported toolchain allows it, and declare the standard with Meson's `c_std` fallback list;
- build with GCC 16.2, Clang 23 or MSVC 14.51;
- gate CI on the OpenSSF hardening guide dated 2026-08-20.

Three of this repository's dated beliefs are wrong or out of date:
- **CISA's memory-safety roadmap date.** It is now "by the end of 2025", and the ask comes from CISA and the FBI, not the NSA.
- **GCC `-fanalyzer` and C++.** GCC 16 "starts to be usable on small C++ examples".
- **The glibc version for `_FORTIFY_SOURCE=3`.** glibc's own release notes put level 3 in glibc 2.33 for Clang 9+ and in glibc 2.35 for GCC 12+. Red Hat's "2.34" matches neither.

**Method note.** The search budget ran out before some Priority sub-points could be checked against primary sources. Those points are marked "unverified" or listed in section 10. No code example was compiled; each is marked "not compiled" with the compiler and flags it is meant for.

## TL;DR

- **Default C modes, October 2026.** GCC 15+ defaults to `-std=gnu23`. Clang (22 and 23) still defaults to `gnu17` and rates its C23 support "Partial". MSVC offers `/std:c11`, `/std:c17` and `/std:clatest`, with C23 core language "Partial". A portable Meson project should therefore declare `c_std=c17` (or `gnu17,c17`) and use C23 features only behind checks.
- **Hardening.** Follow the OpenSSF Compiler Options Hardening Guide (2026-08-20 revision). It recommends `-D_FORTIFY_SOURCE=3`, `-fstack-protector-strong`, `-fstack-clash-protection`, `-Wl,-z,relro -Wl,-z,now`, PIE, and `-ftrivial-auto-var-init=zero` for production. It says blanket `-Werror` belongs in development only, never in distributed sources. Ubuntu builds most of these flags into its GCC. Debian and Fedora apply them only through package build flags, and Debian still uses `_FORTIFY_SOURCE=2` and leaves `-z now` off by default.
- **Policy.** Version 2 of CISA and the FBI's "Product Security Bad Practices" (January 2025) moved the memory-safety roadmap ask to "by the end of 2025". For a small open-source C program, a roadmap means a published, prioritized plan: hardening flags, sanitizers and fuzzing in CI, and a view on which input-facing components could move to a memory-safe language.

## 1. Summary

1. C23 is ISO/IEC 9899:2024. The next revision, C2y, is not published. The newest working draft is N3886 (2026-05-24). WG14 filed a "C2Y Schedule" paper (N3827, 2026-03-01), and an LLVM issue reports that "WG14 seemingly starts determining C2Y as C29 (per WG14 N3827)". N3827 itself was not read in this run.
2. GCC's current release is 16.2 (2026-08-07). GCC 16.1 (2026-04-30) changed the C++ default to GNU C++20, but the C default stays `gnu23`, which GCC first adopted in 15.1 (2025-04-25).\[1\]
3. GCC 13 reached end of support with 13.5 on 2026-09-11. The supported GCC branches are now 14, 15 and 16.
4. Clang defaults to `gnu17` "if no -std option is specified" and lists C23 as "Partial". Clang 22 made `-Wincompatible-pointer-types` an error by default (secondary source).
5. MSVC has had `/std:c11` and `/std:c17` since Visual Studio 2019 16.8. C23 support is "Partial", through `/std:clatest`. MSVC Build Tools 14.52 is due stable in November 2026 with Visual Studio 18.12.
6. Meson 1.12.1 (2026-09-22) is current. Feature releases arrive roughly every four months (1.10.0 on 2025-12-08, 1.11.0 on 2026-04-13, 1.12.0 on 2026-08-10). Meson 1.12 requires Python 3.10 or later, and `werror=true` now also passes the linker's fatal-warnings flag.
7. `meson.options` is the current options filename (since Meson 1.1). `meson_options.txt` is the name used before 1.1.
8. Meson's `warning_level=3` maps to `-Wall -Wextra -Wpedantic` on GCC and Clang and to `/W4` on MSVC. `b_sanitize` became a free-form array in Meson 1.8. `b_lundef=true` (the default) conflicts with AddressSanitizer for Clang shared libraries.
9. The OpenSSF hardening guide's current revision is dated 2026-08-20. It adds `-fzero-call-used-regs=used-gpr` on x86_64 and aarch64, and the C-specific `-Werror=implicit -Werror=incompatible-pointer-types -Werror=int-conversion`.
10. `-D_FORTIFY_SOURCE=3` needs GCC 12+ or Clang 9+ and optimization at `-O1` or higher. glibc's release notes put the glibc floor at 2.33 with Clang 9+ and 2.35 with GCC 12+.
11. Ubuntu builds these into its GCC: `_FORTIFY_SOURCE=3` (since 24.04), stack-protector-strong, stack-clash protection, `-fcf-protection` (x86), PIE, relro and now. Debian's dpkg-buildflags uses `_FORTIFY_SOURCE=2` and leaves `bindnow` disabled. Fedora's redhat-rpm-config uses `_FORTIFY_SOURCE=3` and `-z now`.
12. GCC 16's static analyzer "starts to be usable on small C++ examples". It is still mainly a C tool.
13. glibc 2.38 added `strlcpy` and `strlcat`. POSIX.1-2024 lists both (secondary confirmation).\[2\]
14. The 2025 CWE Top 25 ranks Out-of-bounds Write #5, Path Traversal #6, Use After Free #7, Out-of-bounds Read #8 and OS Command Injection #9. It adds three buffer-overflow entries (CWE-120, -121, -122). Integer Overflow (CWE-190) dropped out.
15. The June 2025 CISA and NSA information sheet "Memory Safe Languages: Reducing Vulnerabilities in Modern Software Development" covers making non-memory-safe code safer during a transition, not only rewrites.

### 4.1 Standards and compilers (Priority 1)

**C23.** Published as ISO/IEC 9899:2024 (F1).\[10\] New features listed by cppreference's C23 page (secondary; https://cppreference.com/c/23):
- `nullptr` and `nullptr_t`;
- `true`, `false`, `bool`, `static_assert` and `thread_local` as keywords;
- `[[attributes]]`: `deprecated`, `fallthrough`, `maybe_unused`, `nodiscard`, `noreturn`, `reproducible`, `unsequenced`;
- `#embed`, `#elifdef`, `#elifndef` and `#warning`;
- `_BitInt`, binary literals, digit separators and the empty initializer `= {}`.

Clang's status page lists `typeof`/`typeof_unqual`, `constexpr` objects (N3018, Clang 19), `#embed` (Clang 19) and "Towards Integer Safety" N2683, which is `<stdckdint.h>` (Clang 18) (F15–F17). **The belief list for C23 is confirmed.**

**C2y.** Not published; the working draft is N3886, dated 2026-05-24 (F2). WG14 has a "C2Y Schedule" paper, N3827 (F3), which was not read in this run. An LLVM issue (https://github.com/llvm/llvm-project/issues/184053) says "WG14 seemingly starts determining C2Y as C29 (per WG14 N3827)", and Wikipedia's article is now titled "C29 (C standard revision)" and says it is "planned for release in late 2029". Both are secondary sources, so the target year is still not confirmed from a primary source.

Early C2y work in compilers:

**GCC.**
- Defaults to `-std=gnu23` (F4), first in 15.1 (F5).
- Current release is 16.2 (2026-08-07). Supported branches are 14, 15 and 16 (F7, F8).
- GCC 16 changed only the C++ default, to GNU C++20 (F6).
- Support window: each major branch gets roughly annual point releases and closes about three years after its .1. GCC 13.1 came out in April 2023 and the branch closed with 13.5 in September 2026 (F8).
- **Inference, flagged:** GCC 14 (14.1 in May 2024) will likely close with 14.5 in mid-to-late 2027, possibly within 12 months. GCC has not announced this.

**Clang.**
- Defaults to `gnu17` (F11), still true in Clang 23 (F12, secondary). C23 support is "Partial" (F13).

### 4.2 Warnings and how CI gates on them (Priority 2)

**The recommended set (F38).** The OpenSSF guide's always-on compile-time flags are `-Wall -Wformat -Wformat=2 -Wconversion -Wimplicit-fallthrough -Werror=format-security`. It adds:
- `-Wtrampolines` and `-Wbidi-chars=any` on GCC;
- `-Werror=implicit -Werror=incompatible-pointer-types -Werror=int-conversion` for C.

Its Table 1 also lists `-Wextra` and `-Wsign-conversion`.

What each flag catches, per the guide's descriptions:

| Flag | Catches |
|---|---|
| `-Wall -Wextra` | "constructs often associated with defects" |
| `-Wformat=2` | "additional format function warnings" |
| `-Wconversion -Wsign-conversion` | "implicit conversion warnings" |
| `-Wimplicit-fallthrough` | switch cases that fall through |
| `-Werror=format-security` | non-literal format strings used without arguments |

**Noise.**
- `-Wconversion` and `-Wsign-conversion` usually produce the most warnings in existing code. The guide's advice for existing projects is to "enable one or a few options at a time".
- `-Wshadow` is **not** in the OpenSSF list; no source recommending it was found.
- Meson's `warning_level=everything` is too noisy to gate on. It maps to `-Weverything` on Clang, all known warning flags on GCC, and `/Wall` on MSVC (F32).

**`-Werror` against a count of warnings.**
- OpenSSF supports `-Werror` "during development but not when distributing source" (F39).
- Since Meson 1.12, `werror=true` also makes linker warnings fatal (F28). That is one more reason not to put `werror=true` in the `default_options` of a project you distribute.
- A setup that follows the guide: a CI job on a pinned toolchain with `-Dwerror=true`, plus a release build without it.
- Gating on a count of warnings is a reasonable engineering pattern, but **no primary source was found** for it.

**MSVC.** Meson maps `warning_level=3` to `/W4` (F32). The `/analyze` documentation was not fetched (section 10).

### 4.3 Hardening (Priority 3)

The OpenSSF guide, revision 2026-08-20 (F38), recommends this base set for GCC and Clang:

```
-O2 -Wall -Wformat -Wformat=2 -Wconversion -Wimplicit-fallthrough \
-Werror=format-security \
-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3 \
-D_GLIBCXX_ASSERTIONS \
-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST \
-fstrict-flex-arrays=3 \
-fstack-clash-protection -fstack-protector-strong \
-Wl,-z,nodlopen -Wl,-z,noexecstack \
-Wl,-z,relro -Wl,-z,now \
-Wl,--as-needed -Wl,--no-copy-dt-needed-entries
```

It adds flags by situation:

| Situation | Additional flags |
|---|---|
| Executables | `-fPIE -pie` |
| x86_64 | `-fcf-protection=full -fzero-call-used-regs=used-gpr` |
| aarch64 | `-mbranch-protection=standard -fzero-call-used-regs=used-gpr` |
| GCC | `-Wtrampolines -fzero-init-padding-bits=all` |
| Production code | `-fno-delete-null-pointer-checks -fno-strict-overflow -fno-strict-aliasing -ftrivial-auto-var-init=zero` |

GCC 14+ also offers `-fhardened`, a "pre-determined set of hardening options".

Minimum versions:
- `_FORTIFY_SOURCE=3` needs GCC 12+ or Clang 9+ and `-O1` or higher (F40). glibc's release notes put the glibc floor at 2.33 with Clang 9+ and 2.35 with GCC 12+ (C3).
- `-fstack-clash-protection` needs GCC 8 or Clang 11.

Distribution defaults, from the subagent's check of primary sources:

| Flag | Ubuntu (in GCC itself) | Debian (dpkg-buildflags, packages only) | Fedora (redhat-rpm-config, packages only) |
|---|---|---|---|
| `_FORTIFY_SOURCE` | 3 since 24.04, at -O1+ | 2 | 3\[37\]\[38\]\[42\] |
| `-fstack-protector-strong` | yes (14.10) | yes | yes\[37\]\[38\]\[42\] |
| `-fstack-clash-protection` | yes except 32-bit ARM (19.10) | yes on amd64/arm64/armhf/armel | yes except armhfp\[37\]\[38\]\[42\] |
| `-fcf-protection` | x86 (19.10) | amd64 (+ `-mbranch-protection=standard` arm64) | x86_64\[37\]\[38\]\[42\] |
| PIE | yes (`--enable-default-pie`) | yes, from Debian's GCC | yes (hardened builds)\[37\]\[38\]\[42\] |
| `-z relro` | yes | yes | yes\[37\]\[38\]\[42\] |
| `-z now` | yes (16.10) | **no** ("Disabled by default") | yes (hardened builds)\[37\]\[38\]\[42\] |

Sources for the table:
- Ubuntu: https://wiki.ubuntu.com/ToolChain/CompilerFlags, last edited 2024-03-22, so it may not reflect 25.10 or 26.04.
- Debian: https://manpages.debian.org/testing/dpkg-dev/dpkg-buildflags.1.en.html (dpkg 1.23.11, 2026-09-09).
- Fedora: redhat-rpm-config's buildflags.md, read through a GitHub mirror because the official src.fedoraproject.org copy could not be fetched; and https://fedoraproject.org/wiki/Changes/Add_FORTIFY_SOURCE=3_to_distribution_build_flags.
- RHEL 9 and 10 defaults were not found in a primary source.

Rules for a project:
1. Always pass `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3`, the guide's form. This avoids redefinition warnings against a distribution's level-2 define and never weakens a level-3 distribution.
2. Never put `-D_FORTIFY_SOURCE=2`, `-fno-stack-protector`, `-no-pie` or `-z lazy` in project flags.
3. In Meson, prefer `b_pie=true` (default false) to hand-written `-fPIE`.
4. Pass hardening flags through `cc.get_supported_arguments()`, so MSVC and older compilers do not fail on them.

```meson
# not compiled — Meson >= 1.3, GCC 12+/Clang 16+
cc = meson.get_compiler('c')
hardening = cc.get_supported_arguments(
  '-U_FORTIFY_SOURCE', '-D_FORTIFY_SOURCE=3',
  '-fstack-protector-strong', '-fstack-clash-protection',
  '-fstrict-flex-arrays=3', '-fcf-protection=full',
  '-Wformat=2', '-Wconversion', '-Wimplicit-fallthrough',
  '-Werror=format-security', '-Werror=implicit',
  '-Werror=incompatible-pointer-types', '-Werror=int-conversion')
add_project_arguments(hardening, language : 'c')
add_project_link_arguments(
  cc.get_supported_link_arguments('-Wl,-z,relro', '-Wl,-z,now',
                                  '-Wl,-z,noexecstack'),
  language : 'c')
```

Meson's `debug` buildtype compiles at `-O0` (Meson's buildtype table: "debug | true | 0"). At `-O0`, `_FORTIFY_SOURCE` does nothing (F40), so CI hardening jobs should use `debugoptimized` or `release`.

### 4.4 Sanitizers and dynamic analysis (Priority 4)

**Sourced in this run:**
- Meson's `b_sanitize` has accepted an array since 1.8, and `address,undefined` is the usual pair (F33).
- `b_lundef=true` breaks ASan with Clang shared libraries, so set `-Db_lundef=false` in that job (F34).
- The OpenSSF guide treats instrumented builds as "instrumented test code", separate from production code, and says both should pass the test suite.

**Unverified in this run.** The following is from general knowledge; check https://clang.llvm.org/docs/AddressSanitizer.html and the sibling pages before filing.

| Tool | Finds | Limits |
|---|---|---|
| AddressSanitizer (ASan) | out-of-bounds access, use-after-free, double free | typical slowdown about 2x |
| UndefinedBehaviorSanitizer (UBSan) | signed overflow, bad shifts, misaligned and null access | — |
| LeakSanitizer | memory leaks | built into ASan on Linux |
| ThreadSanitizer (TSan) | data races | cannot be combined with ASan or MSan |
| MemorySanitizer (MSan, Clang only) | reads of uninitialized memory | cannot be combined with ASan; all code, including libc++, must be instrumented |
| Valgrind Memcheck | memory errors without a rebuild | about 10–50x slower; does not work on ASan builds |

To check that a binary really is instrumented, ask the binary rather than trusting a log line:
- `nm -D ./prog | grep -q __asan_init` for ASan;
- look for `__ubsan_handle_` symbols for UBSan;
- or run it with `ASAN_OPTIONS=help=1`, which prints options only from an instrumented binary.

### 4.7 C security — the `c-security` module (Priority 7)

Each item gives the safe pattern. Items without a fetched primary source are marked.

**Buffers and strings.**
- Prefer APIs that carry the buffer length.
- `strlcpy` and `strlcat` exist in glibc 2.38 and later (F45) and in POSIX.1-2024 (F46, secondary). Detect them with `cc.has_function('strlcpy', prefix : '#include <string.h>')`.
- If `snprintf` returns a value at least as large as the buffer, the output was truncated; check for it.
- `strncpy` does not NUL-terminate when the source fills the buffer, and it pads short strings with zeros. This is standard C behaviour but was not re-verified in this run.
- The removal of `gets` in C11 and the optional status of Annex K were not re-verified (section 10).
- Use `-fstrict-flex-arrays=3` and GCC 16's `counted_by` (F10) so FORTIFY can check bounds on flexible arrays.

**Format strings.** Never pass outside data as the format string; write `printf("%s", s)`. Enforce this with `-Wformat=2 -Werror=format-security` (F38).

**Integer overflow.** Signed overflow is undefined behaviour. Use C23's `<stdckdint.h>`, available in Clang 18+ (F15); GCC 14+ support was not verified in this run.

```c
/* not compiled — intended: gcc 15 -std=c23 -Wall -Wextra -O2 */
#include <stdckdint.h>
#include <stddef.h>
#include <stdlib.h>
void *alloc_array(size_t n, size_t size) {
    size_t total;
    if (ckd_mul(&total, n, size)) return NULL;  /* true means overflow */
    return malloc(total);
}
```

OpenSSF also recommends `-fno-strict-overflow` for production (F38). CWE-190 (integer overflow) left the 2025 Top 25 (F58), but it remains a root cause of CWE-787 and CWE-122.

**Paths from outside data.** Path Traversal is #6 in 2025 (F57).\[43\] The safe pattern follows POSIX semantics, not re-verified in this run:
- reject names that contain `/` or equal `.` or `..`;
- reject absolute paths;
- open relative to a directory file descriptor with `openat(dirfd, name, O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0600)`;
- never `stat()` and then `open()`; that is a time-of-check-to-time-of-use race (CWE-367);
- on Linux 5.6+, `openat2` with `RESOLVE_BENEATH` keeps path resolution inside the directory (not verified in this run).

```c
/* not compiled — intended: gcc 16 -std=gnu17 -D_GNU_SOURCE -Wall -O2 */
#include <fcntl.h>
#include <string.h>
int create_in_dir(int dirfd, const char *name) {
    if (name[0] == '\0' || strchr(name, '/') ||
        strcmp(name, ".") == 0 || strcmp(name, "..") == 0)
        return -1;
    return openat(dirfd, name,
                  O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW | O_CLOEXEC, 0600);
}
```

**Running programs.** OS Command Injection is #9 and Command Injection #23 (F57). CISA lists "Inclusion of User-Provided Input in Operating System Command Strings" as a bad practice and asks that "command inputs are clearly delineated from the contents of a command itself" (quoted via https://www.insideprivacy.com/cybersecurity-2/cisa-and-fbi-publish-product-security-bad-practices/, secondary). Use `posix_spawn` or `execve` with an argument array. Never pass outside data to `system` or `popen`.

**Temporary files, environment and locale.** Use `mkstemp`, not `tmpnam` or `mktemp`. In privileged code, treat `getenv`, `LANG`/`LC_*` and `TMPDIR` as controlled by an attacker, and use `secure_getenv` on glibc. Not re-verified in this run.

**Logs and terminals.** Before writing outside text to a log or terminal, escape control characters (below 0x20, 0x7f, and bytes that start terminal escape sequences) and CR/LF. The relevant weaknesses are CWE-117 (log injection) and CWE-150. Not re-verified in this run. GCC's `-Wbidi-chars=any` (F38) covers Trojan-source characters in the source code itself.

**CWE Top 25 (2025) entries that apply to C** (F57, MITRE's own list): CWE-787 (#5), CWE-22 (#6), CWE-416 (#7), CWE-125 (#8), CWE-78 (#9), CWE-120 (#11), CWE-476 (#13), CWE-121 (#14), CWE-122 (#16), CWE-20 (#18), CWE-77 (#23), CWE-770 (#25). No 2026 list was found.

**SEI CERT C.** The OpenSSF guide cites it as "SEI CERT C[CMU2016C]", which is consistent with a 2016 edition. Whether the wiki is still maintained was **not found**.

### 4.8 Memory-safety guidance (Priority 8)

Timeline:
- **December 2023:** "The Case for Memory Safe Roadmaps" (CISA, NSA and partners).
- **October 2024:** CISA/FBI "Product Security Bad Practices" version 1, asking for a roadmap "by January 1, 2026", with an exemption for products whose end of support is before 1 January 2030 (F55).
- **January 2025:** version 2, asking "by the end of 2025" (F54) and adding three new bad practices.
- **June 2025:** the CISA/NSA "Memory Safe Languages" information sheet (F56).

The CISA documents say a roadmap should cover "priority code components (e.g., network-facing code or code that handles sensitive functions like cryptographic operations)", and that new product lines should use memory-safe languages. The guidance is not binding.

What a roadmap means in practice for a small open-source C program (this report's recommendation, drawn from those documents): a `SECURITY.md` or `docs/memory-safety.md` that
1. names the components that parse outside input (here: hardware data, and files named from it);
2. commits to the OpenSSF flags, ASan and UBSan, and fuzzing in CI;
3. says whether, and in what order, those components could move to a memory-safe language, or why not;
4. is dated and revisited at each release.

### 4.10 Mistakes AI assistants make in C (Standard 10)

No published study of AI assistant errors specific to C was found in this run. These mistakes, seen in this run's sources, are ones an assistant is likely to make:

- writing `c_std=gnu11` alone in Meson, which warns on MSVC and will become an error (F37);

### 4.11 Legacy C (Standard 11)

What changes on the way to C17 or C23, from sources read in this run:
- C23 makes `bool`, `true`, `false`, `static_assert`, `thread_local`, `alignas` and `alignof` keywords (F17). Code that defines them as macros or typedefs breaks, and GCC 15's `gnu23` default turns this into compile errors for old code.
- OpenSSF's `-Werror=implicit -Werror=incompatible-pointer-types -Werror=int-conversion` targets "obsolete C constructs removed by the 1999 C standard".
- Clang 22 treats incompatible pointer types as an error by default.
- GCC 15 changed what `{0}` clears in a union (F42).

Not verified in this run: C23 removes K&R (old-style) function definitions and makes `f()` mean `f(void)`. `ATOMIC_VAR_INIT` is removed (the Clang docs cited for F17 list this).

Safe path: compile with `-std=gnu17` first under the full warning set and fix what it finds, then try `-std=c23` in a separate CI job.

## 8. Review checklist

| Check | What to look for | How bad if missing | Fix |
|---|---|---|---|
| Standard declared | `c_std` in `project()` default_options, with fallback list | Medium: behaviour changes across GCC 15/Clang | `'c_std=gnu17,c17'` |
| Minimum Meson | `meson_version` matches features used (`meson.options` needs 1.1, `c_std` list 1.3) | Low–medium | Set `meson_version : '>=1.3.0'` |
| Options file | `meson.options` present, not only `meson_options.txt` | Low | Rename |
| Warning level | `warning_level=3` plus OpenSSF extras via `get_supported_arguments` | Medium | Add flags list (4.3) |
| Werror policy | No blanket `werror=true` in distributed defaults; CI job sets `-Dwerror=true` on a pinned toolchain | Medium | Move to CI |
| FORTIFY | `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3`, optimized builds | High for input-handling code | Add; use `debugoptimized` in CI |
| Stack/CFI/RELRO/PIE | stack-protector-strong, stack-clash, cf-protection, `-z relro -z now`, `b_pie=true` | High | Add |
| No weakening flags | No `-fno-stack-protector`, `-no-pie`, `-z lazy`, `_FORTIFY_SOURCE=2` | High | Remove |

| Size arithmetic | `ckd_mul`/`ckd_add` or explicit checks before `malloc` | Critical | 4.7 example |

| Static analysis | `-fanalyzer` and clang-tidy run in CI | Medium | Add job |
