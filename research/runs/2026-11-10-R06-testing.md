- pytest 9.2.0 (27 October 2026) is current, so that belief holds.\[2\] The Hypothesis half also holds: its PyPI page (version 6.170.9, 23 October 2026) says "Hypothesis is the property-based testing library for Python."
- Jest 30 did ship in 2025 (4 June 2025) and is now at 30.5.x.\[3\]\[4\] **Vitest 5.0 shipped 3 September 2026 and 5.1 on 2 November 2026**, so "Vitest 3 or 4" is out of date.\[5\]
- Playwright 1.65.0 (5 November 2026) is current. It adds Bun support and a failures-only reporter, has breaking changes in cookies, proxy credentials and inert elements, and no longer tests on Node.js 20.\[6\]\[7\]\[8\] "Most widely used" was not verified.
- .NET: xUnit.net v3 4.0.0 (14 August 2026), MSTest 4.5.2 (27 October 2026), **NUnit 5.0.0 (27 September 2026)** and TUnit 1.76.x.\[9\]\[10\]\[11\]\[12\] "NUnit 4" is out of date.
- PHP: **PHPUnit 13 (6 February 2026) is current**, not 12. PHPUnit 12 bug fixes end 5 February 2027, and PHPUnit 14 is planned for 5 February 2027. **Pest 5 (28 July 2026) is current**, and Pest 4 bug fixes end 28 July 2027.\[13\]\[14\]
- Java: JUnit 6.0.0 shipped 30 September 2025, confirmed by JUnit's own 6.0.0 release notes ("Date of Release: September 30, 2025"). The current stable release is 6.1.3 (7 August 2026).

- Flaky tests: Google, Microsoft and GitHub all detect flaky tests by automatic rerun, keep flaky failures off the critical path through quarantine or suppression, and file a bug for an owner automatically. All three warn that hiding flaky failures can mask real defects.\[20\]\[21\]\[22\]
- At scale, mutation testing is done incrementally on changed code during code review, with filtering of uninteresting ("arid") mutants.\[23\] Petrović et al. ("Practical Mutation Testing at Scale", arXiv:2102.11378) describe this as how Google made it work in an environment where "Google has a codebase of two billion lines of code and more than 500,000,000 tests are executed on a daily basis."
- `claude plugin eval` (Claude Code v2.1.269 or later) runs each case three times with the plugin and three times without it, then reports WITH, W/OUT and Δ. It excludes "skill fired" graders from the score so they cannot inflate Δ.\[24\]\[25\]
- Priority questions 1, 3 and 4 (test strategy, test doubles, coverage) and most of questions A–G and 6–11 were **not covered** in this run. They are listed in section 9 and should be a follow-up run (R06b).

### Q5. Flaky tests
- **Google (Micco, 27 May 2016).** Google reported "a continual rate of about 1.5% of all test runs reporting a "flaky" result." It also found that "about 84% of the transitions we observe from pass to fail involve a flaky test!" Its practices: rerun, a flaky marker that "report[s] a failure only if it fails 3 times in a row", and a tool that "automatically quarantines the test … and files a bug". The post warns that quarantining "could easily mask a real race condition."\[22\]
- **Microsoft (Lam et al., ICSE 2020).** The Flakes system in CloudBuild "automatically retries the test once by default", files bug reports automatically, and suppresses failures for 30 days "to discourage developers from fully relying on suppressions". It "automatically removes the test from the suppression file" when the bug closes. By the paper's count, "Flakes has created over 4,000 bug reports".\[21\] The product equivalent is Azure DevOps flaky-test management. Its docs say: "If a test case fails initially but passes on a rerun, it is marked as flaky." The docs page itself is undated; the feature was announced in Sprint 155 (2019).\[52\]
- **GitHub (Raine, 16 December 2020).** GitHub retries "in the same process", "shifted into the future", and "on a different host", which identifies "90 percent of flaky failures". It gives each flaky test an impact score and, above a threshold, "an issue is automatically opened and assigned to the people who most recently modified either the test files or associated code".\[20\]
- **Position:** use the shared pattern. Detect by rerun, keep flaky failures from blocking merges, and always pair suppression with an expiring, owned bug. Never use rerun alone.

### A. Checks that can't fail
Partly covered. Google's published practice runs mutation analysis on changed lines during code review.\[23\] It drastically reduces "the number of mutants by omitting lines of code without statement coverage and lines that are determined to be uninteresting - we dub these *arid lines.*" (ACM abstract, ICSE-SEIP 2018).\[53\] The 2021 TSE paper reports evaluation "with more than 24,000 developers on more than 1,000 projects".\[40\] Where to apply it: run mutants on the checker or grader's own diff so a weakened check is surfaced in review.

The claude plugin eval design gives a second, directly relevant pattern. A grader that cannot fail without the plugin, such as "skill fired", is excluded from the score "so counting it would push the without-arm toward zero and inflate `Δ`".\[25\] Sources specifically on mutating test oracles or graders, and on testing the "couldn't check" path, were **not found**.

### Q10. Testing AI features and agent skills
`claude plugin eval` is documented at https://code.claude.com/docs/en/plugin-evals.
- Each case is "a realistic prompt plus one or more graders". The grader types are `regex`, `tool_used`, `tool_order`, `file_exists`, `llm` and `baseline`, and "There are no custom-code graders."\[25\]
- "Each case runs three times by default." A case passes when its mean score meets `--threshold`, which defaults to `1.0`.\[25\]
- On the baseline: "If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass."\[25\]
- On judge stability: "An `llm` grader asks a model for a verdict, so its answer can differ between runs, and it differs more the longer the text it has to read." Grade long outputs with `regex` instead.\[25\]
- Every run is a real model call and is billed.\[25\]
- **Contested or evolving:** one secondary post, written against Claude Code 2.1.259, called the command early access with no public docs. The docs page now exists and states v2.1.269 as the minimum.\[25\]\[54\] Trust the docs and `claude plugin eval --help`.

## 7. Common mistakes

- **Treating a rerun pass as a fix.** Google warns that auto-rerun "encourages developers to ignore flakiness in their own tests" and that quarantine "could easily mask a real race condition" (testing.googleblog.com, 2016-05-27). Microsoft time-limits suppression to 30 days for the same reason (ICSE 2020).\[21\]\[22\]
- **Reporting an eval score without a baseline.** "If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass." (code.claude.com plugin-evals)
- **Using an LLM judge on long output.** Use `regex` for long files and keep `llm` rubrics short, with concrete PASS and FAIL conditions (same source).\[25\]
- **Pester 5 syntax under Pester 6.** `Assert-MockCalled` and `Set-ItResult -Pending` are removed, and the legacy `Invoke-Pester -Script ... -CodeCoverage` parameters are gone (pester.dev v5-to-v6).\[36\]
- **Mixing `b.N` and `b.Loop`.** "Benchmarks should use either b.Loop or a b.N-style loop, but not both." (antonz.org, secondary)\[60\]
- **Installing nextest without `--locked`.** Such builds "are, and will remain, broken" (nextest README).
- **Upgrading Go and seeing `go build` pass while `go test` fails.** Under Go 1.27, `stdversion` runs in `go test` (go.dev/doc/go1.27).\[17\]\[61\]
- **AI coding assistants' specific failure modes** (asserting current output, weakening tests, mocking the subject): **no primary sources found in this run.**
